# المعمارية — MaxCare Reception Assistant

## نظرة عامة

## الوضع الحالي (2026-11-04) — وسيط السيرفر بدل جهاز الموظف

```
┌───────────────────┐   POST /api/insurer/job     ┌───────────────────────┐
│ الإضافة (العميل)   │ ───────────────────────────►│ maxcall.local:3001     │
│ popup+background   │                              │ /api/insurer/* (LAN)   │
└───────────────────┘                              └──────────┬─────────────┘
      │  GET /job/<id> (استطلاع)                              │ 127.0.0.1:3011
      ▼                                                       ▼
  HIS: شريط التقدم                                  maxcall-broker.service
                                                     عامل Playwright دائم لكل
                                                     تأمين (طابور تسلسلي)
```

- **MedNet** مكتمل وموجود: دخول → تحقق → Print ← PDF يجلب مباشرة في ≤ 6 ث.
- **NextCare** معدّة للمرحلة التالية على نفس المحرك.
- **Liva** لحق لاحقاً مع معالجة الكابتشا (المهوّلـة في الوسيط + عقدة 15 ث).
- الإضافة لا تفتح نافذة تأمين إطلاقاً — لا نوافذ، لا تبويبات، أخف جهاز استقبال.

```
┌─────────────────────────┐        ┌──────────────────────────────┐
│ Chrome — جهاز الاستقبال │        │ السيرفر maxcall.local:3001    │
│                         │        │ (خدمة maxcall-dashboard)     │
│ popup ──► background ───┼──(1)──►│ /api/his/patient/<id>        │
│                 │       │  Basic │        │                     │
│                 ▼       │  auth  │        ▼                     │
│ tabs: التبويبات         │        │ his_broker (JWT يُجدَّد ذاتياً) │
│  ├─ solverserver:81     │        │        ▼                     │
│  │   his-reader         │        │ Solver WebHIS 192.168.1.77   │
│  └─ موقع التأمين        │        │ (قراءة فقط)                  │
│      bridge + adapter   │        └──────────────────────────────┘
└─────────────────────────┘
```

1. الـbackground يطلب بطاقة التأمين من السيرفر بمصادقة Basic (بيانات جهاز MaxCall).
2. السيرفر يستعلم WebHIS عبر `his_broker` — التوكن JWT يعيش على السيرفر ويُجدَّد تلقائياً
   (صلاحية 100 يوم، تجديد قبل 65). **المتصفح لا يرى أي أسرار HIS.**
3. الـbackground يفتح/يعيد استخدام تبويب موقع التأمين ويرسل الحمولة للمحوّل (content script).

## مكونات ونموذج الرسائل

### الرسائل (chrome.runtime / chrome.tabs messaging)

| الرسالة | الاتجاه | الغرض |
|---|---|---|
| `his:detect` | popup → background | العثور على تبويب المشفى وقراءة المريض النشط |
| `his:readPatient` | background → his-reader | مسح صفحة المشفى وإرجاع `{patId, source}` |
| `his:patient` | popup/background → background | استدعاء `/api/his/patient/<id>` |
| `insurer:run` | popup → background → tab | بدء/متابعة تشغيل محوّل شركة التأمين |
| `insurer:probe` | popup → tab | وضع الاستكشاف: عرض الحقول والأزرار المرشحة |
| `job:status` | popup → background | سؤال عن حالة مهمة جارية |
| `adapter:progress` | content → popup/background | تقارير تقدم الخطوات (`{step, status, detail}`) |

### دورة حياة المهمة (job) — لماذا إعادة الإرسال؟

مواقع NextCare/MedNet تعمل بـpostbacks وإعادة توجيه كاملة (WebForms) أو PPR (ADF) —
أي أن state داخل الصفحة يفقد عند كل تنقل. لذلك:

- الـbackground يحفظ المهمة في `jobs` (خريطة `tabId → {card, creds, stage, ...}`، مهلة 3 دقائق).
- عند كل `tabs.onUpdated (status=complete)` لتبويب المهمة تُعاد إرسال `insurer:run`
  مع **المرحلة الحالية** (`stage`) — المحوّل بلا حالة، يقرأ الصفحة والمرحلة ويقرر.

المراحل: `null → (login) → after_login → (eligibility) → awaiting_result → (document) → done`.

المحوّل يحدد المرحلة الجديدة بإرسال `adapter:progress`، والـbackground يخزنها في `stageAfter()`.

### كشف المريض النشط

`his-reader.js` يُستدعى عند الطلب فقط (لا مراقبة مستمرة — صفر كلفة على الأداء) ويجرّب:

1. أنماط في الـURL (hash/queries)
2. حقول إدخال مرئية بقيم رقمية قرب تسميات مثل "Patient ID / File No / رقم الملف"
3. نص معروض بصيغة `Patient ID: 5080625`

عند الفشل يظهر إدخال يدوي في الـpopup (خطة بديلة دائمة).

## استراتيجية الجلسات

| الموقع | الآلية |
|---|---|
| HIS | JWT على السيرفر فقط — لا شيء في المتصفح |
| NextCare | كوكيز الجلسة في التبويب المعاد استخدامه؛ عند انتهائها المحوّل يعيد الدخول **صامتاً** (بلا CAPTCHA) |

## قرارات تصميمية (ولماذا)

1. **أتمتة داخل الصفحة (content scripts) لا نداءات API للمواقع:**
   أغلب هذه البوابات تولّد المستند القابل للطباعة عبر postback/PPR، وتزوير الطلبات
   هش ضد تحديثاتها وقد يخالف شروط الاستخدام. محاكاة سلوك مستخدم حقيقي أبطأ بثوانٍ لكنها أصلب.
2. **إعادة استخدام تبويب واحد لكل شركة:** يبقى الداشبورد محمّلاً (SPA/PPR أسرع) ولا تتراكم تبويبات.
3. **الطباعة مباشرة وبلا مشاهدة:** موقع التأمين يعمل داخل **نافذة مخصصة مصغّرة** (خارج نظر
   الموظف). عند الوصول للمستند تُستعاد النافذة ويُستدعى `window.print()` فيظهر مربع الطباعة
   مباشرة. خيار autoPrint (افتراضي: مفعّل).
4. **التعبئة بـnative value setter + أحداث input/change:** حتى تلتقطها طبقات
   Angular/jQuery/Ajax.NET في صفحات المواقع.
5. **تنبيه تلقائي للمتابعة (3 ثوانٍ) بعد تعبئة رقم العضوية:** يوازن بين الأتمتة والأمان —
   إن احتاج الموقع خياراً (النوع/القسم) تتوقف الأتمتة وتنتظر قرار الموظف.
6. **لماذا لا Tailwind CDN في الـpopup:** Manifest V3 يمنع تحميل كود عن بُعد (CSP
   `script-src 'self'`) — أي CDN سيرفضه المتصفح، وبناء Tailwind بـpipeline كامل يضيف
   تعقيداً لا يتناسب مع حجم واجهتين صغيرتين. لذلك CSS مضمن يدوياً بتصميم token-based بسيط.
7. **كلمات المرور:** في `chrome.storage.local` فقط (خاصة بالبروفايل) ولا تُكتب في أي ملف
   مصدري. أمن جهاز الاستقبال = قفل حساب Windows.

## خارطة الطريق — المرحلة الثانية: النسخة السيرفرية (الهدف النهائي)

الواجهة الحالية (نافذة مصغّرة + content scripts) هي **مرحلة استكشاف** قصيرة الأجل:
تخفف عبء الموظف اليوم وتجمع لنا خريطة كل موقع بدقة. أثناء كل تشغيل يسجل الـbackground
(صلاحية `webRequest`) كل طلب POST داخل مواقع التأمين في اللوج:

```
[net] POST https://pulse-uae.nextcarehealth.com/ajax/Nextcare.EligibilityChecking2,... | {...}
```

بعد جلسات قليلة سنملك: endpoints الاستعلام الحقيقية، أسماء الحقول، سلوك الجلسات.
حينها تُبنى **وحدة سيرفرية** (مكتبة جلسات لكل شركة على `maxcall.local`):

- السيرفر يحتفظ بجلسات مواقع التأمين (كوكيز/JWT) ويجدد الدخول بنفسه
- الـExtension يصبح رقيقاً جداً: نقرة → `POST /api/insurer/<id>/eligibility` → السيرفر
  يستخرج المستند → PDF يُفتح في مربع الطباعة محلياً
- صفر تبويبات على أجهزة الاستقبال (أخف بكثير على الأجهزة الضعيفة)، بيانات الدخول مركزية
  على السيرفر فقط، والصيانة مركزية (تغيير في موقع شركة = تحديث السيرفر وحده)
- CAPTCHA (Leva) تُحوَّل كصورة للـpopup ليحلها الموظف ثم يكمل السيرفر

آلية الاكتشاف للتقاط الطلبات تعمل من الآن — كل استخدام حقيقي يقربنا من هذه النسخة.
